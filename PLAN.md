# Read-Only Apple Ads MCP

## Combined product, security, implementation, and release plan

**Status:** Executed — Phases 1–3 built and live-verified (0.2.x, 2026-09-22); Phases 4–5 delivered with 0.1.0. Decisions in §18 taken on 2026-09-02; validation log in §21; live deviations from this plan are in docs/API_NOTES.md.
**Date:** September 2, 2026
**Deployment model:** Open-source software; each user deploys a private instance in their own Google Cloud project or runs it locally
**Safety posture:** Permanently read-only
**Sibling project:** [unofficial-reddit-ads-mcp](https://github.com/goncaloaguer/unofficial-reddit-ads-mcp) — same architecture, same principles; this document only spells out what is Apple-specific and inherits the rest by reference.

---

## 1. Executive decision

Build an open-source, analysis-first Model Context Protocol (MCP) server for the **Apple Ads Platform API** (the API that replaced Apple Search Ads Campaign Management API v5, which sunsets January 26, 2027). It lets an authorized advertiser inspect account structure, pull reports, diagnose delivery, analyze keyword and search-term performance, and use Apple's insights, suggestions and recommendations — without modifying anything in Apple Ads.

The implementation reuses the Reddit server's proven shape:

- Python 3.11+, official MCP Python SDK / FastMCP, stateless Streamable HTTP for Cloud Run and stdio for local clients.
- A thin, policy-enforcing `httpx` client with an exact read-operation registry (see the ADR in §3.4 for why we do not build on Apple's official SDK).
- Mandatory ad-account allowlist, personal-use execution ceilings, no database, no payload logging.
- Unofficial-project disclaimer; the maintainers do not operate a shared hosted service.

v1 scope is **App Store campaigns only** (`promotedObjectType: APPSTORE_APP`). Apple Maps (`BUSINESS_BRAND`) endpoints are classified in the registry as read-only but *disabled*, so they can be enabled by a later reviewed change without touching the safety model.

## 2. Non-negotiable principles

Identical to the Reddit plan §2 (permanently read-only; analysis-first; single advertiser per deployment; minimal data retention; deterministic calculations with explicit interpretation). Apple-specific consequences:

### 2.1 Read-only with no read-only OAuth scope

Apple's OAuth flow has exactly one scope, `searchadsorg`. Unlike Reddit's `adsread`, **the scope cannot express read-only** — write capability is decided by the API user's *role* on each ad account. Therefore:

- Read-only remains a property of the program: no write operation exists in the registry; no create/update/delete/bulk/upload/apply/dismiss code exists in the codebase; no configuration can enable one.
- Documentation instructs operators to invite the API user with the **API Account Read Only** role (or *Limited Access API Read Only*). This is defense in depth on Apple's side, not the primary control.
- At startup the server calls `GET /v1/acls`, filters to the allowlisted accounts, and **warns** when the role set includes a write-capable role (`Admin`, `API Account Manager`, `Limited Access API Read & Write`, or an unrecognized role). Setting `APPLE_ADS_REQUIRE_READONLY_ROLE=true` turns that warning into a startup failure. Default is warn, not refuse, because Apple's role-name list is not a closed enum in the API (`roles` is `List[str]`) and a hard refusal on an unknown name would strand users. A refused start never weakens the structural guarantee.

### 2.2 POST is not a read signal

Apple uses `POST /v1/{entity}/query` for every list/search read **and** `POST /v1/{entity}` for every create. The Reddit registry's loader defense ("enabled entries may only be GET or POST") is therefore insufficient here. The Apple registry loader enforces a stricter structural rule: an enabled `POST` must have a path ending in `/query`, or be the single explicitly reviewed exception `POST /v1/search/geo` (a lookup by IDs). Any path containing `/apply`, `/dismiss`, `/bulk-`, or `/upload` is refused at load time regardless of classification. This rule is tested (§14.2) and was validated against all 99 operations (§21).

### 3.2 API facts to encode

| Topic | Fact |
|---|---|
| Base URL | `https://api.ads.apple.com/v1/` |
| Token endpoint | `POST https://appleid.apple.com/auth/oauth2/token`, `grant_type=client_credentials`, `scope=searchadsorg`; access token TTL 3600 s, `token_type: Bearer` |
| Client secret | A JWT you sign with your ES256 (P-256) private key: header `{alg: ES256, kid: keyId}`, claims `iss=teamId`, `sub=clientId`, `aud=https://appleid.apple.com`, `iat`, `exp` ≤ 180 days after `iat`. `clientId`, `teamId`, `keyId` are shown in the Ads UI after uploading the public key (Account Settings → API). |
| Required headers | `Authorization: Bearer …` on everything; `X-AP-Context: adAccountId={id}` on every ad-account-scoped call. Not required for `GET /v1/me`, `GET /v1/acls`, `GET /v1/orgs/{id}`, `GET /v1/advertiser-resources` (which itself requires `?resourceType=CONTENT_PROVIDER\|BUSINESS_BRAND`); optional for `shared-budgets`. (Apple's SDK sends `adAccountId={id};` with a trailing semicolon; the docs show it without — we send the documented form and verify tolerance live, §3.3.) |
| Account discovery | `GET /v1/me` → `{userId, orgId}`; `GET /v1/acls` → `result.acls[] = {adAccount:{id,name,orgId}, roles:[…]}`; `GET /v1/ad-accounts/{id}` → `currency`, `timezone`, `paymentModel`, `systemStatus[Reasons]`, `productFeatures[]` (docs name the values `APPSTORE_APP_MANUAL` / `BUSINESS_BRAND_MANUAL`; the SDK types the array as plain strings — treat as opaque, verify live), `delegations[]`. Ad-account IDs are integers. |
| Querying — four request families | Offset pagination everywhere — **no `next_url`**, so the Reddit SSRF pagination validator is unnecessary; caps on offset/pages/rows replace it. But the SDK shows **four distinct body schemas**, and `apple/query.py` must build each: (a) *entity* `/query` (campaigns, adgroups, ads, keywords, negative-keywords, creatives, shared-budgets): `QueryFilter{field, operator, value, ignoreCase?}` (operators include `EQUALS, IN, LIKE, STARTS_WITH, CONTAINS_ANY/ALL, IS_NULL…` — no `CONTAINS`; "name contains" = `LIKE` + `ignoreCase`), `QuerySort{field, order}`, `QueryPagination{offset, pageSize, fetchTotalCount}`; empty body = all non-deleted entities. (b) *reports and insights*: `Filter{field, operator, value}` (has `CONTAINS`, no `ignoreCase`), `Sorting`, `RequestPagination{offset, pageSize}` — **no `fetchTotalCount`**; rely on response `pagination.totalCount`. (c) *recommendations and suggestions*: `RecommendationFilterCondition{field, operator, value: [..] (always an array), ignoreCase?}`, pagination `{offset, pageSize ≤ 1000, default 20}`; per-endpoint required filters: daily-budget/target-CPA recommendations need `promotedObjectId` = **campaign ID**; keyword suggestions accept campaign or app ID; phrase/category suggestions require `queryType: SUGGESTION\|SEARCH`; target-CPA suggestion needs `promotedObjectId` = app ID + `promotedObjectType: APPSTORE_APP`, optional `countryOrRegion`, and is rate-limited to 5 QPS. (d) *change history*: `AuditFilter`, `Pagination{offset, pageSize}`, `options.needTotals` as the **string** `"true"\|"false"`. |
| Response envelope | `{result, pagination:{offset,pageSize,totalCount}, error}`; some endpoints return `{error:{code,message,details:[{code,message}]}}`. HTTP: 400 `bad_request`, 401 `unauthorized`, 403 `forbidden`, 404 `not_found`, 429 `rate_limit_exceeded`, 500. |
| Rate limits | Every response carries `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` (delta seconds); 429 adds `Retry-After` (prefer it). Apple's guidance: back off proactively when Remaining is low; double the wait per consecutive 429 up to ~16 s. |
| Reports | `POST /v1/reports/apps/{campaigns\|adgroups\|ads\|keywords\|searchterms}/query`. Body: `timeRange:{start, end, timeZone: UTC\|ORTZ, granularity?: HOURLY\|DAILY\|WEEKLY\|MONTHLY}`, `filters`, `sorting`, `pagination` (pageSize ≤ 5000, default 100), `fields?`, `groupBy?`, `options:{includeRows:[GRAND_TOTAL, EMPTY_METRICS]}`. Rows: `{totalMetrics, granularMetrics?[], metadata}`; `summary.grandTotal` when requested. |
| Report metrics (Apps) | `localSpend`, `impressions`, `taps`, `ttr`, `cpt`, `cpm`, `tapInstalls`, `tapInstallCPI`, `viewInstalls`, `totalInstalls`, `totalNewDownloads`, `totalRedownloads`, `tapNewDownloads`, `tapRedownloads`, `viewNewDownloads`, `viewRedownloads`, `totalAvgCPI`, `totalInstallRate`, `tapInstallRate`, `tapPreOrdersPlaced`, `viewPreOrdersPlaced`, `totalPreOrdersPlaced`. Money fields are `{amount, currency}` objects. No conversion/revenue metrics exist in-platform. |
| Report groupBy (Apps) | campaigns/ad groups: `deviceClass, ageRange, gender, countryCode, adminArea, locality, storefront, countryOrRegion`; keywords & search terms: `deviceClass, storefront, countryOrRegion`; ads: `storefront, countryOrRegion`. `HOURLY` granularity excludes `ageRange, gender, countryCode, adminArea, locality` (SDK). `options.includeRows` is not supported for the search-term level (SDK); docs add that `EMPTY_METRICS` cannot be combined with `groupBy`. Keyword report rows carry `insights.bidRecommendation`; search-term rows carry `metadata.searchTermText`, `searchTermSource`, `keyword{id,text,matchType,bid}`, `adGroupId`, `campaignId`. |
| Granularity limits | HOURLY: range must start within last 7 days; not for ads or search terms. DAILY: start within last 90 days, range > 1 day. WEEKLY: start within 365 days, end ≥ 14 days ago. MONTHLY: end ≥ 90 days ago. Single-day request: omit granularity. Search terms: `ORTZ` only. |
| Insights | `POST /v1/insights/apps/impression-share/query` (must filter `promotedObjectId`; DAILY ≤ 30 days or WEEKLY_SUN_SAT ≤ 4 weeks starting on a Sunday; UTC; `options.impressionShareReportType: FIRST_SLOT\|ALL_SLOTS`; rows carry `lowImpressionShare/highImpressionShare`, `rank`, `searchPopularity1to5`). `POST /v1/insights/apps/search-term-popularity/query` (WEEKLY_SUN_SAT or MONTHLY; UTC; dimensions `countryOrRegion, genre, searchTerm, week\|month`; optional `rankInGenre, searchPopularityInGenre, searchPopularity1to100, searchPopularity1to5`; retention is rolling — 65 weeks for weekly (generated Mondays 07:00 UTC), 15 months for monthly (refreshed on the 5th); docs cite data from October 2025). |
| Change history | `POST /v1/change-history/query` — different schema: required `eventTime` filter (`BETWEEN`/`GREATER_THAN`/`LESS_THAN`, max 6-month lookback); other filterable fields per the SDK are `entityType, entityId, userId, userType, txnId, adAccountId, campaignId, adGroupId` with `EQUALS`/`IN` only — **`eventType` is not filterable** (the docs list it; the SDK does not); filter it client-side from `AuditSummary.eventType`. `options:{needTotals: "true"\|"false", timeZone: UTC\|ORTZ, metadata: none\|latest\|snapshot}`. Detail lookup: `GET /v1/change-history/{detailId}` (`limit`/`offset` query params) where `detailId` = `EntityType.entityId.txnId`; the docs say `metadata=latest` populates `metas[].detailId`, the SDK types `metas` as free dicts — construct the ID ourselves and verify live (§3.3). |
| Recommendations & suggestions | Query-only: `/recommendations/daily-budgets/query`, `/recommendations/target-cpas/query`, `/suggestions/{keywords,phrases,categories,target-cpas}/query`. `…/apply` and `…/dismiss` are writes and denied. |
| Campaign status model | `status` (ENABLED/PAUSED, advertiser intent), `systemStatus` (RUNNING/NOT_RUNNING) with `systemStatusReasons[]`, `displayStatus` (exactly RUNNING/PAUSED/ON_HOLD/LIMITED/PROCESSING/DELETED; ad groups add `CAMPAIGN_ON_HOLD`), `systemStatusLimitingReasons[]`; `bidStrategy:{bidStrategyType, bidStrategyGoal}` — types include `MANUAL_CPT, MAX_CONVERSIONS` (App Store) and `MANUAL_CPM, MAX_ENGAGEMENTS` (Maps); goals include `TAP, INSTALL, IMPRESSION`; placements live under `targeting.supplyPlacement.include[]/exclude[]` (with `targeting.supplySource`, `targeting.countryOrRegion`) as opaque strings — the docs' value names (`APPSTORE_SEARCH_RESULTS`, `APPSTORE_TODAY_TAB`, `APPSTORE_SEARCH_TAB`, `APPSTORE_PRODUCT_PAGES`) do not appear in the SDK, so we pass values through untouched and verify live (§3.3); `dailyBudget`, `sharedBudgets` (budget orders). Ad groups: `automatedKeywordsOptIn`, deprecated `cpaCap`. Keywords: `bid`, `matchType` (`EXACT, BROAD, CATEGORY`). |

### 3.3 Known uncertainties to verify live (Phase 0/1)

1. Exact `X-AP-Context` tolerance (with/without trailing `;`).
2. Whether `GET /v1/acls` returns the role strings exactly as the UI names them ("API Account Read Only" etc.) — determines the role-warning table.
3. Whether the `pagination.totalCount` is populated without `fetchTotalCount: true` (docs: no).
4. Money object shape in report rows (`{amount: "12.34", currency: "USD"}` string vs number).
5. Real `RateLimit-Limit` values per endpoint family (docs give the headers, not the quotas).
6. Exact `productFeatures` and `targeting.supplyPlacement` value strings (docs vs untyped SDK fields).
7. Whether change-history `metas[]` carries `detailId`/`entityId` when `options.metadata=latest` (docs say yes; SDK types it loosely). Fallback: build `EntityType.entityId.txnId` ourselves.
8. Whether report `pagination.totalCount` is populated without a request flag (reports have no `fetchTotalCount`).

Each answer goes into `docs/API_NOTES.md`, as with the Reddit project.

### 3.4 ADR-001 — Client layer: thin `httpx` client, not Apple's official SDK

**Decision:** implement the Apple client as a small async `httpx` layer behind the read-operation registry, and use Apple's official Python SDK repository *only* as the pinned source of truth for the operation inventory and model shapes (drift detection).

**Context.** Apple publishes an official, MIT-licensed, Apple-maintained client (`apple-ads-platform`, generated with openapi-generator; handles the OAuth token lifecycle; 374 typed models). It is a good library for read-write integrations. We evaluated building on it.

**Why the thin client wins for this project:**

1. *Read-only must be structural.* The SDK's single `AppleAdsApi` class exposes all 99 operations, including every create/update/delete/bulk/upload/apply. With it, "read-only" becomes a promise our wrapper makes, and the invariant test degrades to "we never call these 36 methods". With the thin client the write code does not exist in the process and the invariant test enumerates every reachable operation.
2. *Same architecture as the Reddit server.* Registry → client → tools → analysis, async end to end, is already reviewed, tested, and deployed. Reuse beats re-review.
3. *Async and composite tools.* The SDK is synchronous (`urllib3`); every call inside FastMCP would need `asyncio.to_thread`, and bounded-concurrency composites become clumsier.
4. *Rate limiting.* The SDK does not act on `RateLimit-*`/`Retry-After`; Apple's own docs show reading them manually via `_with_http_info` tuples. Our `http_policy` layer does this centrally either way.
5. *Dependency surface.* Thin client: `mcp`, `httpx`, `pydantic`, `pyjwt[crypto]` (pulls `cryptography`). SDK adds `urllib3`, `python-dateutil`, `typing-extensions`, and 374 generated modules, and pins Python ≥ 3.12. This process holds ad-account credentials; less surface is better.
6. *Maturity.* The SDK is 19 days old with one commit ("initial release"). Being an early adopter of a generated v1.109.0 client in a credential-holding service is a risk we do not need to take; the API itself is documented well enough to call directly.

**What we keep from the SDK:** its repo is pinned by `spec.version` (109) and commit; `scripts/check_api_drift.py` extracts `(method, path, operationId)` from `apple_ads_api.py` at that pin and diffs against `read_operations.json`. When Apple bumps the spec, CI fails until every new/changed operation is classified — the same gate as the Reddit `openapi/` + `SHA256SUMS` flow, with the SDK standing in for the spec Apple doesn't publish. Model modules are consulted (not imported) when a field shape is ambiguous.

**Consequences.** We own ~40 lines of auth (validated in §21) and the request/response shapes for ~25 read operations actually used by tools. If write tooling is ever wanted, that is a separate repository and the moment to reconsider the SDK.

## 4. Read-only security contract

### 4.1 Exact operation allowlist

`src/apple_ads_mcp/policy/read_operations.json` classifies **all 99** operations from the pinned SDK inventory. Top level: `spec_version`, `sdk_commit`, `operations_sha256`, `counts`. Each entry: `operation_id`, `method`, `path` (with `/v1` prefix), `classification` (`enabled` | `disabled` | `denied`), `reason`, `rate_group`, `paginated`, `sensitivity`, `requires_context` (derived mechanically from the SDK signature: `x_ap_context` absent for `/me`, `/acls`, `/orgs/{id}`, `/advertiser-resources`; optional for shared budgets; required elsewhere).

Result of the reviewed classification (§21): **47 enabled, 16 disabled (Apple Maps, read-only, out of v1 scope), 36 denied (all writes).**

Enabled (App Store scope): `GET /me`, `GET /acls`, `GET /orgs/{id}`, `GET /ad-accounts/{id}`, `GET /advertiser-resources`; campaigns/adgroups/ads/keywords/negative-keywords/creatives/shared-budgets `…/query` + `GET …/{id}`; `GET /campaigns/{id}/legacy-app-limited-status-reason-details`; 5 `reports/apps/*/query`; 2 insights; 2 recommendations queries; 4 suggestions queries; change-history query + detail; `GET /search/apps`, `GET|POST /search/geo`; `GET /apps/{adamId}` + locale-details query; `eligibilities/apps/query`; `rejection-reasons/apps/query` + `GET …/{id}`; product-pages query/detail/locale-details; `metadata/apps/supported-languages/query`.

Denied, always: every `PUT`/`DELETE`; every bare `POST /v1/{entity}` create (`ad-accounts`, `campaigns`, `adgroups`, `ads`, `keywords`, `negative-keywords`, `creatives`, `shared-budgets`, `location-groups`); `keywords|negative-keywords/bulk-create|bulk-update`; `assets/upload`; `recommendations/*/apply|dismiss`.

### 4.2 Defense in depth

| Layer | Control |
|---|---|
| Apple role | Docs mandate a read-only API role; startup ACL check warns (or fails, opt-in) on write-capable roles. |
| MCP authentication | Bearer (default) or explicitly enabled high-entropy secret-path mode; mutually exclusive (inherited unchanged from Reddit). |
| Account isolation | `ALLOWED_ACCOUNT_IDS` (integers) mandatory; `X-AP-Context` is *derived from the resolved allowlisted account*, never from tool input directly. |
| Operation registry | Exact method + normalized path match before every request; loader refuses non-`/query` POSTs (except `/search/geo`) and any `/apply`, `/dismiss`, `/bulk-`, `/upload` path even if the JSON says `enabled`. |
| Tool surface | No arbitrary method/URL/operation tool; no filter passthrough to unknown fields (curated filter vocab per entity). |
| HTTP client | Only `https://api.ads.apple.com` and `https://appleid.apple.com`; redirects disabled; 30 s timeout; no proxy env inheritance (`trust_env=False`). |
| Pagination | Offset/pageSize only, server-capped; `offset` never taken from the model beyond the cap. |
| Tests | Invariants fail if a write method/path becomes reachable or if the loader accepts a mutating POST. |
| CI drift check | Pinned SDK inventory vs registry; new/changed operations must be classified. |
| Runtime configuration | No setting can enable writes. |

### 4.3 Account authorization

- `ALLOWED_ACCOUNT_IDS`: comma-separated integer ad-account IDs; mandatory on HTTP transport; validated `^[0-9]+$`.
- `DEFAULT_ACCOUNT_ID` optional and must be allowlisted; auto-set when exactly one account is allowlisted.
- `list_ad_accounts` calls `/acls` and returns only allowlisted accounts, enriched by `GET /ad-accounts/{id}` (currency, timezone, systemStatus, productFeatures). Accounts whose `productFeatures` lack `APPSTORE_APP_MANUAL` are returned with a warning that v1 tools target App Store campaigns.
- `orgId`/`userId` from `/me` are used only for `orgs/{id}` context; user emails never appear (Apple does not return them; change history returns `modifiedBy`/`userId`, which we pass through as opaque IDs).

## 5. Intended users and supported workflows

Same primary users as Reddit (advertiser, agency-per-client instance, analyst over stdio, developer on Cloud Run). Primary workflows for Apple Ads:

1. Discover allowlisted ad accounts and their apps (`promotedObjectId` = adamId).
2. Review campaigns, ad groups (bids, targeting, automation), keywords (bid, match type), negative keywords, ads and creatives.
3. Pull performance across the five App Store report levels with granularity, groupBy, and filters.
4. Compare periods, rank entities, trend metrics, check pacing against `dailyBudget`.
5. Mine search terms: which terms convert, which are not yet keywords, which deserve negatives.
6. Keyword efficiency: bid vs CPT, TTR, install rate, impression share headroom.
7. Diagnose delivery: `systemStatusReasons`, `displayStatus`, ad rejection reasons, app eligibility, budget/payment states.
8. Correlate change history with performance shifts.
9. Plan with Apple's own signals: keyword/phrase/category suggestions, Target CPA suggestions, budget/CPA recommendations (read), search-term popularity.

## 6. MCP capability design

Target: ~24 composable tools + 3 resources + optional prompts.

### 6.1 Account structure

| Tool | Purpose | Upstream |
|---|---|---|
| `list_ad_accounts` | Allowlisted accounts with currency, timezone, status, product features, delegated app content providers. | `/acls`, `/ad-accounts/{id}` |
| `list_campaigns` | Campaigns with budget, bid strategy, targeting (placements, storefronts), status trio and reasons, promoted app. Filters: status, displayStatus, name (`LIKE`, case-insensitive), promotedObjectId. | `/campaigns/query` |
| `list_ad_groups` | Ad groups with bids, automation (`automatedKeywordsOptIn`), targeting dimensions, schedule, status. Filters: campaign IDs, status. | `/adgroups/query` |
| `list_keywords` | Keywords (bid, matchType, status) for ad groups/campaigns; `include_negative=true` adds negative keywords (campaign- and ad-group-level). | `/keywords/query`, `/negative-keywords/query` |
| `list_ads` | Ads with creative refs, status, and rejection reasons resolved to human text. | `/ads/query`, `/creatives/query`, `/rejection-reasons/apps/query` |
| `get_app_details` | App metadata, locales, product pages (custom product pages usable as ad destinations). | `/apps/{adamId}`, locale-details, `/product-pages/query` |

### 6.2 Reporting and deterministic analysis

| Tool | Purpose |
|---|---|
| `get_report` | Flexible report. `level: campaigns\|adgroups\|ads\|keywords\|searchterms`; `start`/`end` (ISO dates); `time_zone: UTC\|ORTZ` (default ORTZ, forced for searchterms); `granularity`; `group_by` (validated per level); `fields`; curated `filters` (campaignId/adGroupId/keywordId IN, status); `include_grand_total`; `max_rows`/`max_pages`. Enforces the granularity windows before calling Apple. |
| `get_daily_performance` | Account KPIs by day for the last N days (DAILY granularity at campaign level, summed): spend, impressions, taps, TTR, CPT, installs (tap/view/total), CPI, new vs redownload. |
| `compare_periods` | Two ranges, absolute/% deltas per entity (`level`). |
| `rank_performance` | Rank campaigns/ad groups/keywords/search terms/storefronts by a metric; cost metrics ascending; `min_spend`. |
| `analyze_trends` | Daily/weekly series with moving average and anomaly flags. |
| `analyze_pacing` | Spend vs `dailyBudget` and shared budgets (budget orders) over the range; `pace_index`. |
| `analyze_keywords` | Keyword-level efficiency: spend, taps, installs, CPI vs bid, TTR, install rate; flags low-impression, high-CPT-vs-bid, zero-install spenders; optional impression-share join. |
| `analyze_search_terms` | Search-term mining: terms with installs not present as exact keywords (expansion candidates), high-spend/zero-install terms (negative candidates), matched keyword and match type. Search-term text is untrusted data. |
| `get_account_history` | Change-history summary for a range (≤ 6 months), optional entity/event/user-type filters; `include_details=true` fetches field-level before/after for up to N changes via `metadata=latest`. |

| Tool | Purpose |
|---|---|

| Tool | Purpose |
|---|---|
| `get_impression_share` | Impression share by search term/keyword for the account's app(s); DAILY ≤ 30 d or WEEKLY_SUN_SAT ≤ 4 w (Sunday-aligned, validated); `report_type: FIRST_SLOT\|ALL_SLOTS`. |

## 7. Common input and output contract

Inherited from Reddit §7 (account resolution, explicit date bounds, bounded IDs, envelope with `data/summary/meta/warnings/derived_metrics`, `truncated` semantics). Apple-specific:

- `meta.source` = `"Apple Ads Platform API v1"`, `meta.time_zone` = `UTC`/`ORTZ` as sent, `meta.currency` from the ad account.

## 9. Authentication and secret setup

### 9.1 Apple authentication

Secrets (Secret Manager → env):

- `APPLE_ADS_CLIENT_ID` (`SEARCHADS.…`)
- `APPLE_ADS_TEAM_ID` (`SEARCHADS.…`)
- `APPLE_ADS_KEY_ID` (UUID)
- `APPLE_ADS_PRIVATE_KEY` — PEM contents (EC `prime256v1`; both `EC PRIVATE KEY` and PKCS#8 accepted) **or** `APPLE_ADS_PRIVATE_KEY_PATH` for a mounted file. Exactly one.

Configuration: `ALLOWED_ACCOUNT_IDS`, `DEFAULT_ACCOUNT_ID` (optional), `APPLE_ADS_REQUIRE_READONLY_ROLE` (default `false`).

Token manager:

- Builds the client-secret JWT in memory per token request (never persisted; `exp` = `iat` + 1 hour rather than Apple's 180-day maximum, since we can sign on demand).
- `POST /auth/oauth2/token` with `grant_type=client_credentials&scope=searchadsorg`; verifies `scope == searchadsorg` and `token_type == Bearer`.
- Caches the access token with a 120 s expiry margin; single-flight refresh lock; one controlled 401 retry per request; never logs tokens or bodies.
- No user agent mandate exists (unlike Reddit); we send `User-Agent: apple-ads-insights-mcp/<version> (+repo URL)`.

No OAuth bootstrap flow is needed: Apple's flow is fully non-interactive after the one-time key upload in the Ads UI. `docs/AUTHENTICATION.md` covers: inviting an API user with a read-only role, `openssl ecparam -genkey -name prime256v1 -noout -out private-key.pem`, `openssl ec -in private-key.pem -pubout`, uploading the public key, reading `clientId/teamId/keyId`, and a `scripts/verify_credentials.py` that gets a token, calls `/me` and `/acls`, and prints the account IDs and roles (nothing else).

### 9.2 MCP client authentication

Unchanged from Reddit §9.2 (bearer default; secret-path compatibility mode; mutually exclusive; constant-time comparison; `/health` endpoint).

## 10. Apple client behavior

- **Pagination:** offset/pageSize loop per request family (§3.2): entity queries send `fetchTotalCount: true` on the first page only; reports/insights have no such flag and use the response `totalCount` if present; change history uses `needTotals: "true"` on the first page; recommendations cap `pageSize` at 1,000. Stop at `totalCount`, `max_pages`, `max_rows`, or a short page. Every page re-sends the full body with only `offset` changed.
- **Rate limits:** parse `RateLimit-Remaining`/`RateLimit-Reset` on every response; if Remaining < 3, sleep `min(Reset, remaining deadline)`; on 429 use `Retry-After` else `RateLimit-Reset` else backoff; double up to 16 s; reset after success; never exceed the tool deadline.
- **Retries:** 429, 500, 502, 503, 504, connection resets; never 400/403/404; 401 once after token invalidation.
- **Errors:** surface `error.code`, `error.message`, and `details[].code/message` (API metadata, not advertiser data — adopting the Reddit post-implementation amendment); never echo bodies otherwise.
- **Compatibility:** unknown enum values preserved raw; unknown response fields preserved; request bodies strict.

## 11. Security and privacy threat model

Reddit §11 applies. Apple-specific additions:

| Risk | Mitigation |
|---|---|
| Private key compromise | PEM only in Secret Manager or a mounted file; never logged; rotation guide (re-upload public key, new `keyId`). |
| Write-capable API role | Structural read-only; startup ACL warning/refusal; docs mandate read-only role. |
| Create-via-POST slip | Loader structural rule + invariant test enumerating every enabled POST path. |
| Cross-account `X-AP-Context` | Header derived only from the resolved allowlisted account; tests assert no tool can set it from input. |
| Prompt injection via search terms / keyword text / app names | Marked untrusted; never interpreted as instructions. |

Logging policy unchanged: never tokens, keys, headers, bodies, entity names, search terms, report rows.

## 14. Test and verification strategy

### 14.1 Unit tests
Money/percent normalization; zero denominators; ORTZ/UTC date handling; granularity-window validation (each of the four rules, boundary dates, single-day rule, ads/search-term HOURLY exclusion); groupBy validation per level; period comparison, ranking, pacing; enum tolerance; allowlist resolution; truncation metadata; error sanitization.

### 14.2 Read-only invariant tests (stdlib-only, run before dependencies are installed)
- Every registered operation matches `read_operations.json`; none is `PUT`/`DELETE`/`PATCH`.
- Every enabled/disabled `POST` path ends in `/query` or equals `/v1/search/geo`.
- No enabled/disabled path contains `/apply`, `/dismiss`, `/bulk-`, `/upload`.
- Registry loader raises on a tampered file that enables `POST /v1/campaigns`.
- Source scan: no string literal for any denied path/operationId in `src/` outside the registry file.
- Token manager requests only `scope=searchadsorg` and rejects a response with a different scope.
- Published tool list contains no mutation semantics.

### 14.3 Contract / drift tests
`spec/operations.json` regenerates deterministically from the pinned SDK commit; `check_api_drift.py` fails on added/removed/changed operations; registry regeneration is deterministic.

### 14.4 HTTP and resilience tests
Offset pagination caps and short-page stop; `RateLimit-*` and `Retry-After` handling; 429 backoff doubling and cap; token refresh concurrency and one-time 401 recovery; partial composite failures; deadlines and size limits; `trust_env=False` and no redirects.

### 14.5 Security tests
Bearer and secret-path behavior (inherited); cross-account attempts (`X-AP-Context` always equals the resolved account); no secrets in logs/health/errors; prompt-like strings in campaign names and search terms; private-key material never in error messages.

### 14.6 Cost/runaway tests and 14.7 integration/release verification
Inherited from Reddit. Live tests require an Apple Ads account with an API user (read-only role) and are disabled by default.

## 18. Approved implementation decisions (2026-09-02)

1. **Posture:** permanently read-only, like the Reddit server.
2. **Client layer:** thin `httpx` client; Apple's official SDK pinned as the drift oracle only (ADR-001, §3.4).
3. **Scope:** App Store campaigns; Apple Maps read endpoints classified but disabled.
4. **Language/framework:** Python ≥ 3.11, `mcp>=1.9,<2` (SDK 2.0 is API-incompatible — same pin as Reddit), `httpx`, `pydantic`, `pyjwt[crypto]`.
5. **Transports:** stateless Streamable HTTP (JSON responses) + stdio.
6. **Hosting:** user-owned Cloud Run; no maintainer-hosted service.
7. **Apple auth:** ES256 client-secret JWT + `client_credentials`, scope `searchadsorg`; read-only API role recommended, startup ACL warning (opt-in refusal).
8. **Remote MCP auth:** bearer default, secret-path opt-in; mutually exclusive.
9. **Account model:** one advertiser per deployment; integer allowlist.
10. **Persistence:** none; bounded in-memory caches.
11. **License:** MIT.
12. **Publication:** GitHub `goncaloaguer/unofficial-apple-ads-mcp`, pushed from the linked Mac.

Open operator inputs (do not block Phase 0–1 code, block live testing): an Apple Ads account with an invited read-only API user and key pair; the ad-account ID(s) to allowlist; which GCP project to deploy to (a dedicated project per the guide, or the existing MCP project).
